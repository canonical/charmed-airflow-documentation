Integrate with Traefik
======================

By default, the Airflow web UI is only reachable from inside the Kubernetes
cluster. Integrating with `Traefik K8s`_ provides a stable external URL so
you can reach the UI from your browser on a local machine, a Multipass VM, or
a remote server.

This guide covers:

* Deploying Traefik and connecting it to the API server.
* Understanding how the two routing modes (path and subdomain) affect your URL.
* Adding TLS with ``self-signed-certificates``.
* Verifying the integration.

Prerequisites
-------------

A running Charmed Airflow deployment. If you haven't deployed it yet, follow
the :doc:`tutorial </tutorial/index>` first.

How ingress works in Charmed Airflow
-------------------------------------

The ``airflow-api-server-k8s`` charm uses the
`ingress per app <https://charmhub.io/traefik-k8s/libraries/ingress>`_
integration. When Traefik provides an ingress URL, two things happen
automatically:

#. The API server restarts with the ``--proxy-headers`` flag and sets
   ``FORWARDED_ALLOW_IPS=*`` so that Airflow trusts the forwarded headers from
   Traefik. This is safe because all traffic has already been gated by the
   cluster network and the ingress controller before reaching the pod.

#. The API server extracts the URL path from the Traefik-provided URL (for
   ``routing_mode=path`` deployments) and shares it with the coordinator. The
   coordinator then sets ``base_url`` in ``airflow.cfg`` across all charms so
   that Airflow generates correct internal links.

Deploy and integrate Traefik
-----------------------------

Deploy the ``traefik-k8s`` charm with trust (it needs Kubernetes RBAC
permissions to manage load balancer resources):

.. code-block:: bash

   juju deploy traefik-k8s --channel=latest/stable --trust

Wait for it to become active:

.. code-block:: bash

   juju status --watch 5s

Then integrate it with the API server:

.. code-block:: bash

   juju integrate airflow-api-server-k8s:ingress traefik-k8s:ingress

After a few seconds, all units should return to ``active/idle``. Traefik
assigns a URL to the API server, which you can retrieve with:

.. code-block:: bash

   juju run traefik-k8s/0 show-proxied-endpoints

The output looks like:

.. code-block:: json

   {
     "proxied-endpoints": "{\"airflow-api-server-k8s\": {\"url\": \"http://10.64.140.43/airflow-airflow-api-server-k8s\"}}"
   }

The inner ``url`` value is the external URL for the Airflow UI.

.. note::

   The IP address (e.g. ``10.64.140.43``) is the MetalLB load balancer IP
   assigned to Traefik. The path (e.g.
   ``/airflow-airflow-api-server-k8s``) is generated by Traefik using the
   ``routing_mode=path`` default.

Routing modes
--------------

Traefik supports two routing modes, configured on the Traefik charm itself.

Path-based routing (default)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

With ``routing_mode=path`` (the default), all applications share a single IP
and are distinguished by URL path:

.. code-block:: text

   http://<traefik-ip>/<model>-<app-name>

For example:

.. code-block:: text

   http://10.64.140.43/airflow-airflow-api-server-k8s

To configure path routing explicitly:

.. code-block:: bash

   juju config traefik-k8s routing_mode=path

Subdomain-based routing
~~~~~~~~~~~~~~~~~~~~~~~~

With ``routing_mode=subdomain``, each application gets its own subdomain:

.. code-block:: text

   http://<app-name>.<model>.<traefik-ip>.nip.io

For example:

.. code-block:: text

   http://airflow-api-server-k8s.airflow.10.64.140.43.nip.io

This requires DNS that resolves wildcards to the Traefik IP. The
`nip.io <https://nip.io>`_ service provides this automatically for IP-embedded
hostnames, so no DNS configuration is needed for local testing.

To switch to subdomain routing:

.. code-block:: bash

   juju config traefik-k8s routing_mode=subdomain

.. note::

   In subdomain mode there is no path prefix, so ``base_url`` in
   ``airflow.cfg`` uses the root path. Both modes are fully supported.

See `Traefik K8s | Configurations <https://charmhub.io/traefik-k8s/configurations>`_ for all
available Traefik configuration options.

Add TLS with self-signed certificates
--------------------------------------

For HTTPS access, integrate Traefik with the ``self-signed-certificates`` charm.
Traefik handles TLS termination — the API server itself always
communicates over plain HTTP inside the cluster.

Deploy the certificates operator:

.. code-block:: bash

   juju deploy self-signed-certificates --channel=1/stable --trust

Integrate it with Traefik:

.. code-block:: bash

   juju integrate traefik-k8s:certificates self-signed-certificates:certificates

Once ready, Traefik will serve HTTPS. Retrieve the new URL:

.. code-block:: bash

   juju run traefik-k8s/0 show-proxied-endpoints

The URL will now start with ``https://``:

.. code-block:: json

   {
     "proxied-endpoints": "{\"airflow-api-server-k8s\": {\"url\": \"https://<Load Balancer IP>/airflow-airflow-api-server-k8s\"}}"
   }

.. note::

   Because the certificate is self-signed, your browser will show a security
   warning. You can safely proceed in local/development environments. For
   production, replace ``self-signed-certificates`` with a CA-backed
   certificates provider such as the
   `LEGO ACME operator <https://charmhub.io/lego>`_.

Access the UI from different environments
------------------------------------------

If your deployment is running in a remote environment or a virtual machine, the Traefik IP address may not be immediately reachable from your local browser. In these scenarios, you must ensure your local machine has a network route to the ingress endpoint.

Common methods for establishing this connection include:

* **SSH Tunneling**: You can use an SSH tunnel to map the remote Traefik port to a port on your local machine. For a conceptual guide and syntax, see the `SSH Tunneling reference <https://www.ssh.com/academy/ssh/tunneling>`_.
* **Static Routing**: You can configure a static route on your host machine to bridge the network gap between your host and the cluster subnet.
* **Ingress Resolution**: For specific details on how the Traefik Ingress charm handles application endpoints, refer to the `Charmed Traefik Ingress guide <https://documentation.ubuntu.com/traefik-k8s-charm/latest/tutorial/tls-termination-using-a-local-ca/#reach-an-application-s-endpoint-with-ingress>`_.

Verify the integration
-----------------------

With the ingress URL in hand, check that the Airflow cluster is healthy:

.. code-block:: bash

   # Extract the URL (strip surrounding quotes)
   URL=$(juju run traefik-k8s/0 show-proxied-endpoints \
     --format=json | jq -r '.["proxied-endpoints"] | fromjson | .["airflow-api-server-k8s"].url')

   curl -s "${URL}/api/v2/monitor/health" | jq

Expected output:

.. code-block:: json

   {
     "metadatabase": {"status": "healthy"},
     "scheduler": {"status": "healthy", "latest_scheduler_heartbeat": "2026-04-16T..."},
     "triggerer": {"status": "healthy", "latest_triggerer_heartbeat": "2026-04-16T..."},
     "dag_processor": {"status": "healthy", "latest_dag_processor_heartbeat": "2026-04-16T..."}
   }

.. note::

   For HTTPS with a self-signed certificate, add ``--insecure`` to the
   ``curl`` command to skip certificate verification in development:

   .. code-block:: bash

      curl -sk "${URL}/api/v2/monitor/health" | jq

Remove the integration
-----------------------

To remove Traefik ingress:

.. code-block:: bash

   juju remove-relation airflow-api-server-k8s:ingress traefik-k8s:ingress

The API server will restart without the ``--proxy-headers`` flag and the
``base_url`` will revert to the internal cluster address. The charm returns to
the same state it was in before the integration.
